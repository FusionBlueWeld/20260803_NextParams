# ParamOptimizer 段階開発設計

> **移行メモ（2026-08-03）**
> このリポジトリには、v000〜v004の実装済みシステムコード、r001初期実装、6工程の共通検証用物理シミュレータ、複合工程検証用物理シミュレータを収録しています。旧開発環境固有の実験データ、ローカルPythonランタイムは含めていません。

## 1. このプロジェクトの目的

このプロジェクトは、実験データから次に試すパラメータ条件を提案し、入力条件と結果の関係を理解するための社内向けツールです。

データ分析や機械学習を専門としない利用者でも、次の流れを段階的に理解できる構成を目指します。

```text
実験データを読み込む
    ↓
未測定条件の結果を予測する
    ↓
次に試す価値が高い条件を選ぶ
    ↓
予測空間と根拠を確認する
```

最初から全機能を提示せず、個別工程を扱うvシリーズと、工程間を扱うrシリーズに分けて機能を追加します。

1. ベイズ最適化による次条件探索
2. ニューラルネットによるパラメータ空間予測
3. GPとNNの統計的ハイブリッドによる予測安定化
4. 技能者の単純な知見、探索範囲、終了判断の導入
5. 個別工程モデルを工程間接続へ渡す共通インターフェース
6. 複数工程の予測空間接続と全体条件調整
7. UIによる可視化と操作

## 共通の擬似実験検証

各バージョンをレーザー溶接・切削・プレス打抜き・熱硬化・熱風乾燥・電解めっきで比較するときは、[validation/README.md](validation/README.md)を最初に確認してください。

`validation/`には、6工程の正解関数、問題定義、単一条件評価・CSV生成・反復探索・横断比較の共通実行器を収録しています。フライス切削と銅電解めっきは8入力・65,536候補の高次元検証にも対応します。`python -m validation.run list` で一覧、`python -m validation.run suite --versions v000 v001 v002 v003 --iterations 2` で接続検証できます。工程の選定根拠は [validation/DESIGN.md](validation/DESIGN.md) にあります。

`multistage_validation/`は既存`validation/`から独立し、塗工→乾燥→熱硬化を接続した決定論的な複合工程oracleを収録します。将来のv004/r001が、個別Best連結、工程間の状態・不確実性伝播、全体条件調整、原因工程推定を正しく扱えるか検証する試験装置です。詳細は [multistage_validation/README.md](multistage_validation/README.md) を参照してください。

## 2. バージョン構成

| バージョン | 主題 | 利用者が理解する内容 | 主な出力 |
|---|---|---|---|
| `v000` | ベイズ最適化 | 実測データから、なぜ次の条件が推薦されるのか | 推薦条件、予測値、制約達成確率 |
| `v001` | NN予測空間 | GP探索と並行して、データ追加によりNN空間がどう変わるか | GP推薦、run別NN予測空間 |
| `v002` | GP–NNハイブリッド | GPのデータ支持度を使って、GPとNNを1つの統計モデルとして融合する | Hybrid推薦、run別Hybrid解空間 |
| `v003` | 技能者知見制約 | 単純な知識をNN損失、探索方針、終了判断へどう反映するか | 知識付きHybrid推薦、知識診断、終了状態 |
| `v004` | r接続インターフェース（暫定） | v003の個別工程モデルを、役割・単位・予測分布付きで工程接続へ渡す方法 | Best候補、stage bundle、条件付き予測口（Robustは検討中） |
| `v005` | UI（暫定） | 予測・不確かさ・推薦を視覚的に確認する方法 | 3D表示、設定画面、再学習 |

rシリーズはvシリーズの後継スナップショットではなく、複数の個別工程モデルを利用する別レイヤーです。

| バージョン | 主題 | 利用者が理解する内容 | 主な出力 |
|---|---|---|---|
| `r001` | 複合工程接続（暫定） | 複数のv004 stage bundleを接続し、最終良品確率と全体条件をどう調整するか | 全体条件案、良品確率、工程別影響、追加実験候補 |

> **実装ステータス（2026-09-09）: v004・r001は現行機能範囲でFIX**
> 修正内容、再検証結果、既知の制限は[FIX記録](V004_R001_FIX_RECORD.md)を参照してください。
> v004はv003互換探索と平均予測stage bundle、r001は直列・固定候補の平均予測接続まで実装済みです。工程入力ばらつきだけを流す実験評価器は、個別工程の閉ループ・予測空間合格後のbundleで独立oracle基準に合格しました。完全観測・期待レシピ既知の条件では、既知NGの工程順位付けと全工程反実仮想回復も物理oracleで検証済みです。ただしモデル誤差の同時サンプリング契約がないため、製品機能としての校正済み確率とはまだ扱いません。潜在原因推定と後戻り実験は後続範囲です。

> **方針更新（2026-09-07）**
> v004はv003のCLI・CSV・日常操作と、追加設定なしでの計算互換を維持し、接続案件だけ任意設定を追加します。r001はbundle能力を検査し、能力不足時には良品確率を未評価とします。詳細は[v004](v004/README.md)と[r001](r001/README.md)を参照してください。

各バージョンは前バージョンの機能を含む累積構成です。ただし、実行時に別バージョンのコードを参照しません。それぞれのフォルダだけでコードが完結する独立したスナップショットとします。

```text
v000  ベイズ最適化
  └─ v001  ベイズ最適化 + NN予測空間
       └─ v002  GP + NN + 統計的ハイブリッド
            └─ v003  知識制約付きNN + 残差GP + 探索/停止方針
                 └─ v004  v003 + r接続用stage bundle（暫定）
                      └─ v005  全機能 + UI
```

```text
複数のv004 stage bundle
  └─ r001  工程グラフ + 不確実性伝播 + 全体条件調整（暫定）
```

### 共通の実行入口

利用者が実行するファイルは、プロジェクト直下の`main.py`だけです。
最初に`--version`で使用する実装を選び、その後へ操作を続けます。

```powershell
python main.py --version v000 --new trial_000
python main.py --version v000 --prepare trial_000
python main.py --version v000 --run trial_000 --n 3

python main.py --version v001 --new trial_001
python main.py --version v001 --prepare trial_001
python main.py --version v001 --run trial_001 --n 3

python main.py --version v003 --new trial_003
python main.py --version v003 --prepare trial_003
python main.py --version v003 --run trial_003 --n 3
```

各バージョンの内部CLIは`src/cli.py`にあり、共通入口から呼び出されます。利用者が直接実行する必要はありません。

## 3. 共通フォルダ構成

すべてのバージョンは、最低限次の構成を持ちます。

```text
v###/
├─ src/                          実際の処理を役割別に配置
│  └─ cli.py                    各バージョン内部の処理順を記述
├─ trials/                       独立した探索案件
│  └─ trial_###/
│     ├─ problem.csv             問題定義
│     ├─ data/experiments.csv    実測結果
│     └─ output/                 そのtrialの出力
├─ README.md                     そのバージョンの目的と仕組み
└─ requirements.txt
```

### 共通`main.py`と`src/cli.py`の責務

プロジェクト直下の`main.py`はバージョン選択だけを担当します。各バージョンの`src/cli.py`はアルゴリズムの詳細を持たず、処理の流れだけを記述します。

想定する形は次のとおりです。

```python
def main():
    data = load_data()
    validated = validate_data(data)
    model = train_model(validated)
    result = run_analysis(model)
    save_result(result)
    print_result(result)
```

利用者は共通`main.py`と選択バージョンの`src/cli.py`を読むことで、「何を入力し、どの順番で計算し、何が出力されるか」を把握できます。

### `src/` の責務

データ読込、入力検査、モデル学習、探索、結果保存などの詳細は `src/` に分離します。

コード量が増えても、外部からの実行入口は `main.py` に統一します。

### `trials/` の責務

工程や目的が異なる探索をtrial単位で分離します。同じ探索で実験結果が増えた場合は、同じtrialの `experiments.csv` に追記します。

v000のtrialは次の3ファイルを中心に扱います。

```text
trial_###/
├─ problem.csv
├─ data/experiments.csv
└─ output/recommendations.csv
```

運用上の必要性が確認できた場合に限り、後続バージョンでモデル評価結果やUI用データを追加します。

## 4. 共通入力データ

入力データは各trialの `data/experiments.csv` へ保存します。上位の `data/` は、原本やサンプルデータの保管場所として使用します。

```text
ParamOptimizer2/
├─ data/
│  ├─ original/
│  │  └─ data.csv
│  └─ samples/
├─ v000/
│  └─ trials/
│     └─ trial_000/
│        ├─ problem.csv
│        ├─ data/experiments.csv
│        └─ output/recommendations.csv
├─ v001/
├─ v002/
├─ v003/
├─ v004/
└─ r001/
```

初期対象データの列は次のとおりです。

| 列名 | 役割 | 内容 |
|---|---|---|
| `id` | 識別子 | 実験番号 |
| `p1` | 入力 | コアモードのパラメータ |
| `p2` | 入力 | リングモードのパラメータ |
| `t` | 入力 | 照射時間 |
| `T` | 出力・制約 | トルク強度 |
| `S` | 出力・目的 | セパレータ熱影響 |

初期の最適化問題は次のように定義します。

```text
目的：Sを小さくする
制約：Tが指定下限以上
```

新しいtrialは `python main.py --version v000 --new trial_000` のように作成し、problem設定後に同じバージョン指定で `--prepare` を実行します。詳細は各バージョンのREADMEを参照してください。

## 5. 全バージョン共通の設計原則

### 5.1 結果と根拠を一緒に出す

推薦条件だけでなく、次を併記します。

- 予測平均
- 予測標準偏差
- 制約を満たす確率
- 実測点からの距離
- 推薦理由
- 補間か外挿か

### 5.2 「予測」と「実測」を区別する

CLIと出力ファイルでは、実測値とモデル予測値を明確に分けます。

予測条件には必ず、実測による確認が必要であることを表示します。

### 5.3 複雑なモデルを自動的に正解としない

モデルの複雑さではなく、条件単位の検証結果を優先します。

同じパラメータ条件の反復データは、学習と検証へ分散させず、同じ分割側に置きます。

### 5.4 外挿を明示する

各入力が最小値・最大値の範囲内でも、入力の組み合わせが実測点から遠い場合があります。

推薦条件には次の分類を付けます。

```text
INTERPOLATION      実測条件に近い
NEAR_BOUNDARY      実測領域の境界付近
EXTRAPOLATION      実測条件から遠い
```

### 5.5 再現性を記録する

乱数を使う処理ではシードを固定し、出力へ記録します。

同じデータと設定で、同じ結果を再生成できることを完成条件とします。

### 5.6 CLIを最後まで残す

`v005` でUIを追加した後も、CLI実行を削除しません。

UIは計算ロジックを直接持たず、CLIと同じ `src/` の機能および生成済み成果物を利用します。

### 5.7 前バージョンを比較基準として残す

新しい方式を実装しても、前バージョンを比較可能な完成版として残します。

```text
v001  GPとNNを独立表示する比較基準
v002  GPとNNを内部融合したHybridとして利用
v003  技能者知見をNN損失・探索・停止へ導入
v004  v003の個別工程モデルへr接続インターフェースを追加（暫定）
```

各バージョンは実行時に他バージョンを参照しません。v002では正式推薦もHybridを使用し、plain GP・独立NNとの比較が必要な場合はv000・v001の同条件trialを実行します。

### 5.8 統計Hybrid・技能者知見・工程接続を分離する

v002では物理式を使わず、GPのデータ支持度を利用してGP予測とNN予測を融合します。

```text
Hybrid(x) = GP(x) + support(x) × {NN(x) - GP(x)}
```

v003では物理式より先に、非負、特定入力に対する単調性、影響小という技能者知見をNN損失へ入れます。使用禁止/好ましい範囲と停止判断は別レイヤーへ分離します。

v003では、具体的な物理式に限定せず、技能者知見を学習したNNを知識アンカーとして扱います。残差GPは実測データでこれを補正し、データ支持が弱い領域では知識付きNNへ戻ります。以前検討した「v004で明示的な物理式アンカーを導入する」計画は削除し、必要性が明確になった場合に別機能として再検討します。

v004は予測方式を別の物理モデルへ置き換える版ではなく、v003までの個別工程最適化をrシリーズから安全に再利用できる形へ公開する版として検討します。r001はその公開成果物を工程グラフ上で接続します。

### 5.9 出力は役割を絞り、run単位で対応させる

利用者が比較する予測空間は、同じrun、同じ学習データ、同じグリッドを使用します。モデル内部の重みや詳細な学習履歴を無条件に増やさず、利用者が確認するCSVを中心に保存します。

## 6. バージョン間で変えないもの

- 入力列の基本的な意味
- プロジェクト直下の`main.py`を唯一の利用者向け入口とする構成
- `src/` への処理分離
- `output/` への根拠保存
- 日本語によるCLIメッセージ
- 実測と予測の明確な区別
- 警告を隠さない方針
- ローカル環境で完結し、外部へデータを送信しない方針
